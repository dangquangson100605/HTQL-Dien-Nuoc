PHẦN 1 — MỞ ĐẦU (1 phút)
================================================================================

Kính chào thầy/cô và các bạn.

Hôm nay nhóm em trình bày dự án **Hệ thống Quản lý Hạ tầng Điện – Nước Đô thị 
dựa trên Bản đồ số** — tên mã HTQL-Dien-Nuoc.

Đây là phần mềm web giúp:
  • Quản lý thiết bị điện/nước và tuyến mạng trên bản đồ Leaflet (Đà Nẵng).
  • Tiếp nhận báo cáo sự cố từ người dân.
  • Phân công kỹ thuật viên (KTV) theo phường/xã.
  • Theo dõi quy trình xử lý có phân quyền rõ ràng: Ai làm gì, lúc nào, 
    hệ thống ghi nhận ra sao.

Tài liệu này không chỉ giới thiệu tính năng — mà giải thích **cách nhóm em 
làm dự án**: từ phân tích bài toán → chọn công nghệ → thiết kế DB → viết API 
→ làm giao diện bản đồ → tự động hóa bằng signal → kiểm thử.

2.1. Bài toán thực tế
----------------------
Ban quản lý hạ tầng điện – nước đô thị cần trả lời các câu hỏi hàng ngày:

  CÂU HỎI                          CẦN HỆ THỐNG LÀM GÌ?
  ─────────────────────────────────────────────────────────────────
  Thiết bị nào đang ở đâu?          Hiển thị trên bản đồ, lọc theo phường
  Trạng thái thiết bị ra sao?       Màu/icon: ACTIVE, FAULT, MAINTENANCE...
  Tuyến nào nối thiết bị nào?       Vẽ polyline điện (cam) / nước (xanh)
  Dân báo sự cố thế nào?            Form + bản đồ, gắn tọa độ + phường/xã
  Ai xử lý sự cố?                   Phân công KTV theo ward
  Đã xử lý xong chưa?               State machine + thông báo + nhật ký
  Tiêu thụ điện/nước bao nhiêu?     ConsumptionLog + tra cứu công khai

2.2. Mô hình hóa — mạng lưới đồ thị (Graph), không phải danh sách rời
-----------------------------------------------------------------------
Nhóm em cố ý mô hình hóa hạ tầng thành **đồ thị**:

  THIẾT BỊ (Device)     = NODE (điểm) trên bản đồ
                          Ví dụ: trạm biến áp, trụ điện, công tơ, bể nước, van...

  TUYẾN (NetworkEdge)   = EDGE (cạnh) nối 2 thiết bị
                          Ví dụ: cáp trung thế TBA → tủ điện, ống nước bể → trạm bơm

  SỰ CỐ (Incident)      = PHIẾU XỬ LÝ gắn vị trí / thiết bị / tuyến
                          Có quy trình trạng thái nhiều bước

  PHƯỜNG/XÃ (Ward)      = ĐƠN VỊ ĐỊA BÀN — nền tảng phân quyền vận hành

  Lợi ích thiết kế:
    • Bản đồ hiển thị trực quan mối quan hệ thiết bị – tuyến.
    • Sự cố gắn device/edge → tự động đổi trạng thái thiết bị sang FAULT.
    • Phân công KTV theo ward của sự cố/thiết bị.

2.3. Phạm vi cố ý giới hạn (phù hợp đề tài môn học)
-----------------------------------------------------
  ✗ Không lan truyền lỗi tự động xuống toàn mạng (chỉ thiết bị/tuyến GẮN TRỰC TIẾP 
    sự cố mới chuyển FAULT; Operator tự quan sát bản đồ đánh giá ảnh hưởng lan).
  ✗ Không có WebSocket/push realtime — thông báo in-app + polling 30 giây.
  ✗ Không tích hợp SCADA/IoT thật — dữ liệu seed mô phỏng.
  ✓ Tập trung Đà Nẵng: 53 phường/xã, 7 quận/huyện.
  ✓ 4 vai trò: ADMIN, OPERATOR, TECHNICIAN, CITIZEN.

PHẦN 3 — KIẾN TRÚC & CÔNG NGHỆ (2 phút)

3.1. Kiến trúc tổng thể
------------------------
  [Trình duyệt]
       │  HTML (Django Template) + Vanilla JS + Leaflet
       │  JWT Bearer token (localStorage) + Django Session cookie
       ▼
  [Django Monolith — một codebase]
       ├── accounts/    → User, RBAC, audit
       ├── assets/      → Device, Edge, Ward, Consumption
       ├── incidents/   → Incident, Notification, Journal
       └── core/        → settings, urls, excel, health
       ▼
  [MySQL qlda_db]  hoặc  [SQLite db.sqlite3 khi test]

  Vì sao Monolith?
    • Dự án môn học cần triển khai nhanh, demo 1 lệnh runserver.
    • Không tách microservices → tránh phức tạp vận hành không cần thiết.

3.2. Xác thực kép: JWT + Django Session
-----------------------------------------
  VẤN ĐỀ: Trang HTML cần session (login_required), JS gọi API cần token.

  CÁCH LÀM:
    1. User POST /api/auth/login/ → nhận access + refresh JWT.
    2. Backend đồng thời gọi django.contrib.auth.login() → tạo session cookie.
    3. Frontend lưu token vào localStorage:
         infra_access, infra_refresh, infra_role, infra_username
    4. Mọi apiFetch() gắn header Authorization: Bearer {access}.
    5. Nếu API trả 401 → tự gọi /api/auth/token/refresh/ → retry.
    6. Refresh thất bại → redirect /login/.

  → Trang server-rendered và API JSON cùng hoạt động an toàn.

3.3. Cơ sở dữ liệu
-------------------
  • Mặc định: MySQL database `qlda_db` (XAMPP localhost, user root, password rỗng).
  • Test/CI: tự chuyển SQLite khi:
      - Biến môi trường USE_SQLITE=True
      - Biến GITHUB_ACTIONS
      - Chạy manage.py test
  • Logic trong core/settings.py — một file, hai môi trường.

3.4. Frontend stack
--------------------
  • Bootstrap 5.3 — layout responsive, modal, form.
  • Leaflet.js 1.9 + OpenStreetMap — bản đồ miễn phí, không cần API key Google.
  • Chart.js — biểu đồ dashboard/analytics.
  • SweetAlert2 — hộp thoại xác nhận đẹp.
  • openpyxl — xuất Excel mẫu văn bản hành chính Việt Nam.
  • Vanilla JavaScript — không React/Vue (tập trung nghiệp vụ, tránh build tool).

PHẦN 5 — THIẾT KẾ CƠ SỞ DỮ LIỆU (4 phút)
================================================================================

5.1. User (accounts.User) — RBAC 4 vai trò
-------------------------------------------
  VAI TRÒ        MÔ TẢ NGẮN                          PHẠM VI ĐỊA BÀN
  ─────────────────────────────────────────────────────────────────────
  ADMIN          Quản trị toàn hệ thống              Toàn thành phố
  OPERATOR       Vận hành, xác nhận sự cố          managed_wards (M2M)
  TECHNICIAN     Xử lý sự cố/bảo trì được giao     managed_wards (M2M)
  CITIZEN        Báo sự cố, tra cứu tiêu thụ        Không có ward scope

  Trường quan trọng:
    role              CharField — ADMIN/OPERATOR/TECHNICIAN/CITIZEN
    managed_wards     ManyToMany → Ward (bắt buộc ≥1 ward cho OPERATOR/KTV)
    failed_login_attempts  → khóa sau 5 lần sai (signal)

5.2. Ward — 53 phường/xã Đà Nẵng
----------------------------------
  code          Mã duy nhất (VD: DN-HC-001)
  name          Tên phường/xã
  district      1 trong 7 quận/huyện
  latitude      Tâm phường (dùng validate tọa độ)
  longitude     Tâm phường
  is_active     Bật/tắt

  Nguồn dữ liệu: assets/data/danang_wards.py
  Lệnh nạp: python manage.py load_danang_wards

5.3. Device — thiết bị hạ tầng
-------------------------------
  LOẠI THIẾT BỊ (device_type):
    ĐIỆN:  TRANSFORMER, DISTRIBUTION_BOX, ELECTRIC_POLE, ELECTRIC_JUNCTION, ELECTRIC_METER
    NƯỚC:  WATER_TANK, PUMP_STATION, MAIN_VALVE, BRANCH_VALVE, WATER_JUNCTION, WATER_METER
    CŨ:    VALVE (legacy)

  TRẠNG THÁI (status):
    ACTIVE       — hoạt động bình thường
    FAULT        — có sự cố / lỗi
    MAINTENANCE  — đang bảo trì
    INACTIVE     — ngừng hoạt động

  Trường quan trọng:
    code, name, latitude, longitude, ward (FK), address, parent (FK self)
    attributes (JSON) — dung lượng TBA, số nhánh tủ điện...

  Trường BẢO TRÌ (workflow riêng):
    maintenance_assigned_technicians (M2M User)
    maintenance_assigned_by, maintenance_assigned_at, maintenance_note
    maintenance_acknowledged_at/by     — KTV xác nhận nhận việc
    maintenance_completed_at/by        — KTV báo xong
    maintenance_result_note            — ghi chú kết quả (bắt buộc khi báo xong)

5.4. NetworkEdge — tuyến nối 2 thiết bị
------------------------------------------
  from_device → to_device (FK Device)
  network_type: ELECTRIC | WATER
  status: ACTIVE | FAULT | MAINTENANCE | INACTIVE
  Unique: một cặp (from, to) chỉ 1 tuyến.

5.5. Incident — sự cố
---------------------
  TRẠNG THÁI (status) — xem PHỤ LỤC D:
    PENDING_VERIFY → CONFIRMED → ASSIGNED → IN_PROGRESS → RESOLVED → CLOSED
    hoặc REJECTED (từ chối)

  Mức độ (severity): LOW, MEDIUM, HIGH, CRITICAL
  Loại (incident_type): ELECTRIC, WATER, OTHER
  target_type: DEVICE | EDGE | UNKNOWN

  Quan hệ:
    reported_by (FK User)           — người báo (thường là CITIZEN)
    confirmed_by                    — Operator xác nhận
    assigned_to                     — KTV phụ trách chính
    assigned_technicians (M2M)      — nhóm KTV
    device / edge (FK, tùy chọn)
    ward (FK, bắt buộc)
    result_note                     — ghi chú kết quả (KTV bắt buộc khi RESOLVED)
    rejection_reason                — lý do từ chối

5.6. Notification — thông báo in-app
-------------------------------------
  recipient, incident/device, notif_type, message, is_read, created_at
  Xem PHẦN 12 để biết khi nào tạo loại nào.

5.7. SystemJournal — nhật ký vận hành (Admin only)
----------------------------------------------------
  actor, category (INCIDENT/MAINTENANCE/SYSTEM), action, summary, details
  incident/device (FK tùy chọn), created_at
  API: GET /api/journal/?category=INCIDENT

5.8. IncidentHistory — lịch sử đổi trạng thái sự cố
-----------------------------------------------------
  Tự ghi qua signal mỗi lần incident.status thay đổi.
  API trả về field history — CHỈ ADMIN thấy (serializer filter theo role).

5.9. ConsumptionLog — tiêu thụ điện/nước
------------------------------------------
  device + date (ngày 1 mỗi tháng) + value
  Unique: 1 thiết bị / 1 tháng / 1 bản ghi.
  Phục vụ: /monitoring/ (nhập liệu) và /lookup/ (tra cứu công khai theo mã công tơ).

5.10. AuditLog — log HTTP thao tác ghi
---------------------------------------
  Middleware ghi POST/PUT/PATCH/DELETE: user, path, method, IP, timestamp.
  Admin xem tại /users/ → tab audit.

PHẦN 6 — CÁCH LÀM BACKEND (TỪNG BƯỚC) (5 phút)
================================================================================

6.1. Bước 1 — Khởi tạo project
-------------------------------
  django-admin startproject core
  python manage.py startapp accounts
  python manage.py startapp assets
  python manage.py startapp incidents

  settings.py:
    AUTH_USER_MODEL = 'accounts.User'
    REST_FRAMEWORK: IsAuthenticated mặc định, JWT auth
    SIMPLE_JWT: rotate refresh, blacklist
    Throttle login: 10 lần/phút
    CORS cho localhost dev

6.2. Bước 2 — Models → Migrations → Seed
-----------------------------------------
  Thứ tự migration quan trọng (phụ thuộc FK):
    assets.0001 Device, Edge
    assets.0006 Ward + device.ward
    accounts.0003 user.managed_wards
    assets.0007 maintenance assignment fields
    assets.0008 maintenance workflow (acknowledge, complete, result_note)
    incidents.0004 incident.ward
    incidents.0005 assigned_technicians M2M
    incidents.0007 SystemJournal + notification types mới

  Lệnh nạp dữ liệu (theo thứ tự):
    python manage.py migrate
    python manage.py load_danang_wards     # 53 phường/xã
    python manage.py seed_data             # thiết bị, tuyến, sự cố, user demo

  seed_data làm gì?
    1. Xóa dữ liệu cũ (device, edge, incident, consumption).
    2. Tạo/reset 4 user demo (admin, operator, technician, citizen).
    3. Gán ward cho operator + technician: 6 quận trung tâm (không Hòa Vang).
    4. Mỗi phường/xã tạo ~18 thiết bị + ~8–11 tuyến (cấu trúc cố định):
         TBA → Tủ điện → 3 trụ điện → 6 công tơ điện
         Bể nước → Trạm bơm → Van tổng → 2 van nhánh → 2 đồng hồ nước
    5. Mỗi phường 1 sự cố mẫu (trạng thái luân phiên) + 3 sự cố đặc biệt toàn thành phố.
    6. 6 tháng tiêu thụ cho mỗi công tơ/đồng hồ.

  Kết quả seed (xấp xỉ):
    ~53 phường | ~950+ thiết bị | ~420+ tuyến | ~56 sự cố | ~2100+ bản ghi tiêu thu

6.3. Bước 3 — Serializers (validate nghiệp vụ TRƯỚC khi lưu DB)
-----------------------------------------------------------------
  DeviceSerializer (assets/serializers.py):
    • ward bắt buộc.
    • latitude/longitude trong [-90,90] / [-180,180].
    • coordinates_match_ward() — tọa độ phải khớp phường đã chọn.
    • parent phải cùng loại mạng (điện/nước).

  IncidentSerializer (incidents/serializers.py):
    • ward bắt buộc (trừ khi auto lấy từ device).
    • Không vừa device vừa edge.
    • target_type=DEVICE → phải có device; target_type=EDGE → phải có edge.
    • coordinates_match_ward() — áp dụng cho CẢ người dân báo sự cố.
    • history field — chỉ trả về nếu request.user.role == ADMIN.

  UserSerializer (accounts/serializers.py):
    • OPERATOR/KTV phải có managed_ward_ids ≥ 1.
    • Register luôn tạo role CITIZEN.

6.4. Bước 4 — ViewSets + @action (endpoint đặc biệt)
-----------------------------------------------------
  DeviceViewSet (assets/views.py):
    CRUD thông thường + lọc theo ward/status/type (spatial filter).
    @action đặc biệt:
      PATCH .../assign-maintenance/           [ADMIN, OPERATOR]
      PATCH .../acknowledge-maintenance/      [TECHNICIAN được giao]
      PATCH .../report-maintenance-complete/  [TECHNICIAN, bắt buộc note]
      PATCH .../confirm-maintenance/          [ADMIN, OPERATOR → ACTIVE]
      PATCH .../update-status/                [theo bảng chuyển trạng thái role]
      GET   .../export-excel/  POST .../import-csv/

  IncidentViewSet (incidents/views.py):
    CRUD + queryset filter theo role:
      CITIZEN     → chỉ sự cố reported_by = mình
      OPERATOR    → sự cố trong managed_wards
      TECHNICIAN  → sự cố được giao HOẶC trong managed_wards
      ADMIN       → tất cả
    @action:
      PATCH .../assign/          Phân công KTV (validate assignable-technicians)
      PATCH .../update-status/   Chuyển trạng thái (VALID_TRANSITIONS + role)
      POST  .../add-note/        Thêm ghi chú tiến độ
      GET   .../stats/           Dashboard KPI
      GET   .../report/          Báo cáo analytics
      GET   .../report-excel/    Xuất Excel

      Nút: "Báo bảo trì xong & gửi vận hành" (+ ghi chú BẮT BUỘC)
      API: PATCH /api/devices/{id}/report-maintenance-complete/
      Body: { note: "Đã thay van, kiểm tra áp suất OK" }

      ★ ĐIỂM NHẤN THUYẾT TRÌNH:
        KTV KHÔNG được tự chuyển ACTIVE.
        Thiết bị VẪN MAINTENANCE — chờ Operator duyệt.
        Operator nhận PENDING_OPERATOR.

  [5] OPERATOR XÁC NHẬN HOÀN THÀNH
      Nút: "Xác nhận hoàn thành & về hoạt động"
      API: PATCH /api/devices/{id}/confirm-maintenance/
      Kết quả: status → ACTIVE, xóa thông tin phân công bảo trì.

  TÁCH TRÁCH NHIỆM:
    KTV    = thực hiện + báo cáo kết quả
    OPERATOR = giám sát + phê duyệt + đưa thiết bị về vận hành

PHẦN 15 — KHÓ KHĂN GẶP PHẢI & CÁCH XỬ LÝ (1 phút)
================================================================================

  1. JWT vs Session
     Vấn đề: Trang HTML cần session, JS cần token.
     Giải pháp: Login API gọi django_login() + trả JWT; frontend lưu cả hai.

  2. Danh sách KTV trống khi phân công
     Vấn đề: URL sai (/api/users/ vs /api/auth/users/), thiếu ?ward=, ward chưa gán.
     Giải pháp: Sửa app.js/incidents.js + dùng assignable-technicians backend.

  3. KTV tự chuyển thiết bị ACTIVE
     Vấn đề: Ban đầu KTV có thể update-status → ACTIVE, bỏ qua Operator.
     Giải pháp: Tách API report-maintenance-complete + confirm-maintenance;
               ẩn nút ACTIVE trên UI KTV; chặn backend.

  4. Tọa độ không khớp phường/xã
     Vấn đề: Click map bất kỳ, chọn ward tùy ý.
     Giải pháp: Haversine validate frontend (app.js, report.js) + backend serializer.

  5. MySQL corrupt trên XAMPP
     Vấn đề: Table exists nhưng engine không đọc được (.ibd mồ côi).
     Giải pháp: Xóa folder mysql/data/qlda_db, DROP/CREATE database, migrate lại.

  6. seed_data lỗi font Windows
     Vấn đề: UnicodeEncodeError cp1252 khi in tiếng Việt.
     Giải pháp: $env:PYTHONIOENCODING='utf-8' trước khi chạy seed.

PHỤ LỤC D — STATE MACHINE
================================================================================

D1. SỰ CỐ (VALID_TRANSITIONS trong incidents/views.py)
────────────────────────────────────────────────────────

  PENDING_VERIFY ──→ CONFIRMED ──→ ASSIGNED ──→ IN_PROGRESS ──→ RESOLVED ──→ CLOSED
        │                │            │
        ├──→ REJECTED    ├──→ REJECTED ├──→ REJECTED
        └──→ ASSIGNED (phân công trực tiếp từ chờ xác minh)

  RESOLVED ──→ IN_PROGRESS (Operator mở lại nếu cần)

  Ai được chuyển gì:
    CITIZEN:     chỉ → CLOSED (sự cố của mình)
    TECHNICIAN:  chỉ → IN_PROGRESS, RESOLVED (sự cố được giao)
    OPERATOR/ADMIN: mọi transition hợp lệ trong VALID_TRANSITIONS

D2. BẢO TRÌ THIẾT BỊ
─────────────────────

  FAULT/INACTIVE
      │ assign-maintenance [OPERATOR/ADMIN]
      ▼
  MAINTENANCE
      │ acknowledge-maintenance [KTV assigned]
      ▼
  (đang sửa)
      │ report-maintenance-complete [KTV, + note]
      ▼
  MAINTENANCE (chờ duyệt — KTV KHÔNG được ACTIVE)
      │ confirm-maintenance [OPERATOR/ADMIN]
      ▼
  ACTIVE
